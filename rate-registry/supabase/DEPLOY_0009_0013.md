# Deploy: migrations 0009–0013 + repo-series seed

The rate-architecture work (server-side benchmark-family resolution, benchmark
history, `repo_markup`/`benchmark_spread`, cohort normalization, benchmark repoint)
plus the matching `app.js`/`style.css` changes. Your prod DB already has 0001–0008,
so only 0009–0013 + the repo seed are new.

**Validated:** the bundle applies clean on a fresh `0001`–`0008` baseline in one
transaction, and `bank_benchmark()` + the floating floor value come out
byte-identical before vs after (the repoint is behaviour-preserving).

## Order matters: DATABASE FIRST, then the frontend

`app.js` now calls `get_repo_markup` and the extended `cohort_stats`. If the new
frontend ships before the DB migration, those RPCs 400 during the gap. So:

1. Apply the SQL (below).
2. Then redeploy the site (Netlify) with the new `app.js`.

## 1. Apply the SQL — pick ONE path

**A. Supabase Studio → SQL Editor (no secret leaves your dashboard — recommended)**
Open your project → SQL Editor → paste the contents of
`rate-registry/supabase/deploy_0009_0013.sql` → Run. It is wrapped in a single
`begin;`/`commit;`, so any failure rolls the whole thing back.

**B. psql with the pooler/direct connection string**
Project Settings → Database → Connection string (needs the DB password):
```
psql "postgresql://postgres:[PASSWORD]@[HOST]:5432/postgres" \
  -v ON_ERROR_STOP=1 -f rate-registry/supabase/deploy_0009_0013.sql
```

Equivalent to running these in order (what the bundle concatenates):
`0009_benchmark_family.sql → 0010_benchmark_history.sql →
0011_normalized_values.sql → 0012_cohort_normalization.sql →
0013_benchmark_repoint.sql → seed_benchmark_history.sql`.

> Note on `seed_benchmarks.sql`: you do **not** need to re-run it. 0013 backfills
> `benchmark_history` from the `benchmarks` rows already in prod. Re-running it is
> safe (it clears + reinserts its own lenders) but unnecessary for this deploy.

## 2. Post-deploy smoke test (SQL Editor)

```sql
select (resolve_benchmark_family('SBI',2021,'Floating')).*;   -- RLLR / high
select benchmark_asof('National','Repo', current_date);        -- 5.25
select count(*) from benchmark_history;                        -- repo series + backfill (~45 on seed data)
```

Then submit a test loan from the live site and confirm the result shows the
"Pricing context" line for a repo-linked bank (e.g. SBI) and nothing for an
HFC/PLR lender (e.g. LIC Housing).

## 3. Frontend / Netlify

The site reads Supabase from build-time env vars (`scripts/write-config.mjs`
writes `config.js`). Set on Netlify → Site settings → Environment variables:
- `SUPABASE_URL` = `https://<your-project-ref>.supabase.co`
- `SUPABASE_ANON_KEY` = your **publishable** key (the `sb_publishable_…` value —
  it works as the anon/public key; RLS protects the data)

Then trigger a redeploy so `config.js` regenerates and the new `app.js` ships.

## Rollback

The SQL is one transaction — a failure during apply leaves prod untouched. After
a successful apply, the change is additive (new columns default NULL, new
functions, an append-only table) and the old wide `benchmarks` table is unchanged
except for `COMMENT`s marking its benchmark-value columns legacy, so reverting is
low-risk if ever needed.
